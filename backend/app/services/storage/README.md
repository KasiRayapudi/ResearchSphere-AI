# Document storage

Where the bytes of an uploaded document live, and how the rest of the
application asks for them.

## Why this exists

Documents used to be written to the local filesystem with the absolute path
recorded in `documents.file_path`. That has two consequences that only show
up in production:

- **The API cannot be scaled.** A second replica cannot read what the first
  one wrote, so ingestion and download both break the moment there is more
  than one process behind the load balancer.
- **The path is host state.** An absolute path in the database describes one
  machine's directory layout. It is wrong after a container restart with a
  different mount, meaningless on another host, and it leaks the server's
  filesystem shape into anything that reads the row.

Business logic now talks to a `StorageProvider` and never learns which one is
behind it. What the database records is an opaque **key**.

## The interface

`base.py` defines `StorageProvider`: `put`, `download_to`, `delete`,
`exists`, `info`, `list`, `signed_url`, `health`. Two rules are worth knowing
before implementing another one:

- **`put()` consumes its source.** On success the file at `source_path` is
  gone. Callers hand over a quarantined upload and are done with it. A
  provider that copied instead would leave a file on local disk on every
  upload — a slow leak on the busiest path in the system.
- **`signed_url()` may return `None`.** A provider that cannot issue a
  time-limited URL says so, and the download endpoint streams the bytes
  itself. Returning a permanent or unauthenticated URL is never a
  substitute.

## Keys

    documents/<workspace-id>/<uuid>.<ext>

Generated by the application, never taken from the client. The client's
filename does not contribute to it, so traversal and overwrite are impossible
by construction rather than by sanitising well enough. `validate_key()` runs
in every provider before anything touches a backend, and the filesystem
provider additionally resolves the path and refuses a result outside its
root.

Partitioning by workspace is what makes the orphan sweep affordable: a
listing can be scoped to one tenant instead of walking everything.

## Choosing a provider

`STORAGE_PROVIDER` is `filesystem`, `s3` or `minio`. Selection happens once,
in `build_provider()`; nothing else imports a concrete provider, and a test
enforces that.

| Provider | When | Downloads |
|---|---|---|
| `filesystem` | development, single node | API streams the file |
| `s3` | production on AWS | 307 to a presigned URL |
| `minio` | self-hosted object storage | 307 to a presigned URL |

`s3` and `minio` are the same class. MinIO speaks the S3 API; the difference
is an endpoint URL and path-style addressing. That is deliberate — the code
path a developer exercises against MinIO is the one that runs against S3.

`azure` is declared and raises. It exists so a deployment that asks for it
gets a clear answer instead of a confusing configuration error, and so
nobody mistakes an empty class for working support.

Invalid configuration fails at startup, not at the first upload:
`validate_configuration()` refuses a production start with `s3` and no
bucket, `minio` without an endpoint, a half-set credential pair, or a signed
URL lifetime outside 30–604800 seconds.

### Running MinIO locally

```bash
docker run -p 9000:9000 -p 9001:9001 -e MINIO_ROOT_USER=minio \
  -e MINIO_ROOT_PASSWORD=minio-secret minio/minio server /data --console-address ":9001"
```

Create a bucket in the console at `localhost:9001`, then set
`STORAGE_PROVIDER=minio`, `MINIO_ENDPOINT=http://localhost:9000`,
`MINIO_BUCKET`, `MINIO_ACCESS_KEY` and `MINIO_SECRET_KEY`.

## Signed URLs

Presigning is pinned to **SigV4**. Left to botocore's default it emits SigV2
(`AWSAccessKeyId`/`Signature`/`Expires`), which every AWS region created
after 2014 rejects outright and which cannot sign SSE-KMS objects — so
downloads would work in development and fail in production. There is a test
that fails if the signature version regresses.

The URL carries `ResponseContentDisposition` so the browser saves the
document under its original filename rather than the opaque key. Quotes and
CR/LF are stripped from that filename: it ends up in a response header.

A signed URL **is** a credential. `SIGNED_URL_EXPIRE_SECONDS` defaults to
300; anyone holding the link can fetch the document until it expires.

## The upload path

1. The upload streams into quarantine, where it is size-checked,
   content-sniffed and virus-scanned. **Quarantine stays local** on every
   provider — validation needs a real file, and nothing unvalidated should
   reach the object store.
2. On success, `storage.put(build_document_key(...), quarantine_path)` moves
   it into storage. `put` runs in a thread pool: for an object store it is
   blocking network I/O and must not sit on the event loop.
3. The row records `storage_provider`, `storage_key` and `storage_metadata`.
   `file_path` is left NULL.
4. If storage fails the quarantined file is discarded and the request returns
   503. No row is created, so there is nothing left pointing at nothing.

The worker fetches through `_document_file()`: the filesystem provider hands
over the file where it already is, an object store is copied to a temporary
file that is removed when the ingest finishes, successfully or not.

## Backward compatibility

Migration `a71c9be40e12` adds the three columns and backfills every existing
row. The backfill is exact rather than a guess: pre-Phase-6 uploads were
promoted into `UPLOAD_DIR` under an opaque generated name, so the basename of
the recorded path is already the key relative to the filesystem root. Nothing
is moved, re-uploaded or rewritten on disk.

`file_path` is kept and only made nullable — dropping it would make a
rollback lossy. `resolve_key()` reads `storage_key` and falls back to the
basename of `file_path`, so a row written before this change is still
downloadable, deletable, and recognised as live by the cleanup sweep.

Legacy objects sit flat at the root of the storage directory rather than
under `documents/`, which is outside the sweep's prefix. Two independent
things therefore protect them, and both are tested.

## Housekeeping

`storage.cleanup` runs daily and reports what it did. It is deliberately
timid, because it deletes user data:

- it looks only under the `documents/` prefix,
- it ignores objects younger than `STORAGE_CLEANUP_GRACE_HOURS` — an upload
  writes the object before it commits the row,
- every candidate is checked against the database, including keys derived
  from legacy paths,
- it stops after `STORAGE_CLEANUP_MAX_DELETES`, so a bug is capped and
  visible in the statistics instead of emptying a bucket,
- each sweep is guarded separately: one failing does not stop the others.

It also removes abandoned quarantine and temporary files older than
`STORAGE_TEMP_RETENTION_HOURS`, and releases the bytes of documents that
failed indexing more than `STORAGE_FAILED_RETENTION_DAYS` ago. That last one
keeps the failure row — the user should still see that the upload failed and
why — and clears the key with the object, so the download endpoint reports
the file as unavailable rather than pointing at something that is gone.

## Switching providers

Configuration change and a restart. No rows are rewritten.

Objects, however, do not move themselves. Documents uploaded under the old
provider stay where they are, and their rows still name that provider. Copy
the objects across before switching if they need to remain reachable — for
filesystem to S3 that is `aws s3 sync <FILESYSTEM_ROOT> s3://<bucket>/`,
which preserves the key layout because the filesystem provider stores keys as
relative paths.

## Rolling back

Downgrading revision `a71c9be40e12` drops the three columns. `file_path` was
never cleared, so rows that predate this work read exactly as they did
before.

Documents uploaded **after** the upgrade have `file_path = NULL` and would
not be readable by the old code. If a rollback is needed and those uploads
matter, run `STORAGE_PROVIDER=filesystem`, copy each object to
`<UPLOAD_DIR>/<basename of key>` and set `file_path` to that path before
downgrading. The alternative — and the reason `file_path` was kept — is to
roll back the application only, leaving the schema at head: the new columns
are additive and nothing older reads them.
